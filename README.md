# MerSI ISM Platform — рабочий прототип

Реализация технической спецификации v6.0 плюс доработки по запросу: модуль
аудита (план/чек-лист/отчёт/ответ ответственного), привязка журналов к
пунктам стандартов с группировкой по требованиям, точки контроля с видимым
статусом «делается / не делается», видимость журналов по пользователю,
табличный вид записей, фильтры и сортировки, левая панель-дерево,
управление ролями и правами. Node.js + Express + PostgreSQL.

**Важно перед запуском.** У меня в контейнере нет доступа к сети — ни
`npm install`, ни прогон против настоящего PostgreSQL я выполнить не смог.
Всё проверено только статически: `node --check` на каждом JS-файле, ручной
подсчёт баланса `<% %>` тегов в каждом EJS-шаблоне, сверка каждого
`res.render(...)` с реально существующим файлом вьюхи, сверка порядка
SQL-плейсхолдеров с порядком элементов в массиве параметров (это самое
уязвимое место при ручном построении SQL). Первый реальный прогон — у вас.

## Быстрый запуск через Docker

```bash
docker compose up -d --build
```

Открыть `http://localhost:3000`.

## Запуск без Docker

```bash
psql -U postgres -c "CREATE USER mersi WITH PASSWORD 'mersi';"
psql -U postgres -c "CREATE DATABASE mersi_ism OWNER mersi;"

cp .env.example .env
npm install
npm run seed
npm start
```

Демо-логины (пароль = логин + `123`):

| Логин | Роль |
|---|---|
| operator | Оператор — видит только назначенные ему журналы |
| quality | Специалист по качеству — видит всю библиотеку, доступ к конструктору/карте/аудитам |
| shift_lead | Мастер смены — видит журналы своего участка |
| storekeeper | Кладовщик — видит складские журналы |
| auditor | Внутренний аудитор — доступ к разделу «Аудиты» |
| director | Руководитель / директор по качеству — видит всю библиотеку |
| admin | Администратор — полный доступ, управление пользователями/ролями |

## Что добавлено в этой версии

### Обратная связь и предохранители (чтобы система помогала, а не молчала)
- **Подтверждение после действия.** Раньше после сохранения записи, закрытия
  несоответствия, отправки отчёта аудита и т.п. человек просто попадал на
  следующую страницу без явного «готово» — не всегда понятно, сработало ли
  действие. Теперь после ключевых действий (создание/проверка/исправление
  записи; весь workflow несоответствия; весь workflow аудита; добавление и
  удаление полей в конструкторе) вверху страницы на секунду-две появляется
  короткое зелёное подтверждение («Запись сохранена», «Аудит начат» и т.п.),
  для отклонений — жёлто-красным. Реализовано без JS-библиотек, через сессию
  (`src/flash.js`), показывается один раз и пропадает при следующем переходе.
- **Подтверждение перед удалением.** Кнопки «убрать поле» в конструкторе и
  «удалить пункт» в шаблоне чек-листа теперь спрашивают подтверждение —
  раньше клик сразу и необратимо (для формы новых записей) убирал поле без
  возможности передумать.

## Что добавлено в предыдущей версии (удобство ведения журналов)
- **Быстрая запись.** Для журналов с коротким набором полей (до 6, без фото и
  таблиц показателей) на странице журнала — что в виде «Список», что в виде
  «Таблица» — теперь есть встроенная компактная форма прямо над списком
  записей: заполнил → нажал «Добавить» → остался на той же странице с тем же
  фильтром → можно сразу вводить следующую запись. Раньше единственным
  способом было уходить на отдельную страницу и возвращаться обратно на
  каждую запись.
- **Полная форма записи** (для журналов с большим числом полей, и как запасной
  вариант при ошибке валидации) переверстана в две колонки вместо одной длинной
  ленты полей — короче прокрутка. Пункты чек-листа (Да/Нет) — крупные
  переключатели вместо мелких радиокнопок. Добавлена кнопка «Сохранить и
  создать ещё» — не нужно каждый раз заново открывать форму. Показывается
  дата последней записи журнала — сразу видно, не задвоили ли ввод.
- **Фильтры и поиск стали компактными.** Везде, где раньше строка фильтров
  занимала заметную часть экрана (библиотека журналов, страница журнала,
  несоответствия, аудиты), теперь это свёрнутая по умолчанию панель
  «Поиск и фильтры ⌄» — разворачивается по клику, если фильтры не пустые,
  раскрыта автоматически. Реализовано нативным HTML (`<details>`), без JS.

## Что добавлено в версии с фото/шаблонами чек-листов

### Фото/файл-подтверждение (по анализу конкурента — GRAIT)
- Новый тип поля в конструкторе (раздел 4.6) — «Фото/файл-подтверждение». Добавляется
  к любому журналу так же, как текст или число; на форме записи превращается в
  `<input type="file">`, до 15 МБ, изображения превью показываются прямо в просмотре
  записи и в табличном виде.
- Тот же тип используется в пунктах чек-листа аудита: при ответе на пункт (или при
  добавлении пункта вручную) можно приложить фото.
- Технически — загрузка через `multer` на диск в `uploads/` (в Docker — отдельный том
  `mersi-uploads`, переживает пересборку), раздача статикой через `/uploads`. Файл
  не привязан к отдельной таблице БД — путь просто хранится как значение поля в
  `values_json` записи (или в `audit_items.photo_path` для пунктов чек-листа).

### Шаблоны чек-листов (`/checklist-templates`)
- Готовые, донастраиваемые наборы пунктов для аудитов — по образцу категорий,
  которые использует GRAIT (пищевая безопасность, экология и охрана труда,
  менеджмент качества). Заранее засеяно 3 стартовых шаблона.
- Администратор/специалист по качеству/внутренний аудитор (право `audit_manage`)
  может: создать новый шаблон с нуля, добавить/удалить/переименовать/переставить
  пункты в любом существующем шаблоне.
- На странице аудита (статус «Идёт») появляется блок «Применить готовый чек-лист»:
  выбираете шаблон — его пункты копируются в аудит как «ожидают ответа»; дальше по
  каждому пункту отвечаете (результат + комментарий + опционально фото) через новый
  роут `/audits/:id/items/:itemId/answer`. Правило автосоздания несоответствия по
  отметке «Замечание»/«Критическое» (раздел 4.1.3) работает и здесь, и для пунктов,
  добавленных вручную.

### Расширенный справочник стандартов
- К шести исходным стандартам добавлены GMP+, ISO 14001, ISO 45001, SQF 2000 —
  чаще всего встречаются у пищевых предприятий с экспортными контрактами.
  Справочник по-прежнему расширяем вручную через карту критических точек.

### Клик по названию журнала
- Мелкая, но заметная правка интерфейса: там, где раньше было название журнала
  текстом плюс отдельная кнопка «Открыть →», теперь само название — ссылка.
  Заодно нашёлся и починен настоящий баг: файл вьюхи `constructor/list.ejs`
  отсутствовал в проекте, из-за чего раздел «Конструктор» падал бы с ошибкой при
  первом открытии.

## Что добавлено в версии с аудитом/ролями

### Модуль аудита (`/audits`)
- План/календарь аудитов: название, стандарт, точка требования, дата,
  аудитор, ответственный за исполнение; фильтр по статусу и датам.
- Жизненный цикл: Запланирован → Идёт → Завершён → Отправлен ответственному
  → Получен ответ → Закрыт.
- Чек-лист аудита: пункты с результатом (Соответствует / Замечание /
  Критическое) и комментарием. Отметка «Замечание» или «Критическое»
  **автоматически создаёт несоответствие** и связывает его с пунктом чек-листа
  — единственный случай автосоздания несоответствия (раздел 4.1.3
  спецификации), как и было задумано изначально для журналов аудита.
- «Отправить отчёт ответственному» переводит аудит в статус «Отправлен»;
  назначенный ответственный (и только он) видит форму «Что будет сделано» —
  пишет план коррекции, после чего аудит переходит в статус «Получен ответ»
  и виден на его дашборде до этого момента отдельным предупреждением.
- Права на создание/проведение аудитов регулируются динамически (см. ниже
  «Роли и права»), а не зашиты в код.

### Несоответствия — корректирующее действие
- У каждого несоответствия появилось поле «Корректирующее действие» —
  исполнитель (или специалист по качеству/руководитель) описывает, что
  именно будет сделано для устранения причины. Доступно из карточки
  несоответствия независимо от того, создано оно вручную или автоматически
  из аудита.
- Список несоответствий получил фильтры: статус, критичность, поиск по
  описанию.

### Журналы — привязка к требованиям и видимость по пользователю
- У каждого журнала по-прежнему есть привязка к точке карты (пункту
  стандарта/ХАССП) — как и в исходном ТЗ. Добавлена страница
  **«Журналы по требованиям» (`/journals/by-requirement`)** — группирует
  всю библиотеку по пунктам стандартов, а не по служебным группам, и
  отдельно показывает журналы без привязки.
- **Видимость журналов теперь персональная.** Администратор, специалист по
  качеству и руководитель видят всю библиотеку. Остальным ролям видны
  только журналы, назначенные администратором в `/admin/users/:id/journals`
  (при первом сидировании демо-пользователям назначены журналы по ключевым
  словам в полях «заполняет»/«проверяет» — дальше это регулирует
  администратор).
- Каталог журналов (`/journals`) получил фильтры: поиск по названию,
  группа, стандарт/требование, тип формы.

### Точки контроля — статус «делается / не делается»
- Страница «Карта критических точек» (`/map`) стала панелью контроля: по
  каждой точке видно, сколько привязанных журналов ведутся вовремя, а
  сколько просрочено (используется тот же движок контроля сроков, что и на
  дашборде).
- Точку теперь можно привязать не только к журналу, но и к регламентному
  отчёту (условно — по коду отчёта из фиксированного каталога раздела 6;
  глубокой интеграции с генерацией самого отчёта нет, это справочная
  привязка «что покрывает этот пункт»).

### Вид записей журнала: список / таблица
- На странице журнала — переключатель вида. «Список» — прежний вид
  (дата/автор/статус). «Таблица» — spreadsheet-стиль: одна строка — одна
  запись, один столбец — одно поле схемы, с сортировкой по клику на
  заголовок столбца.
- На обоих видах — фильтр: поиск по автору и значениям полей, диапазон дат.
- Технически фильтрация и сортировка идут в памяти приложения после
  выборки из БД (значения записей хранятся как JSON-текст, не JSONB) — для
  прототипа с разумным объёмом данных этого достаточно; для промышленной
  нагрузки лучше перейти на JSONB и фильтровать на уровне SQL.

### Левая панель-дерево
- Боковое меню вместо верхней навигации: Дашборд, Журналы (разворачивается
  по группам), Несоответствия, Прослеживаемость, Карта критических точек,
  Аудиты, Отчёты, Инструменты (конструктор — только у ролей с правом),
  Администрирование (только admin).
- Кнопка сворачивания/закрепления панели — состояние запоминается в
  `localStorage` браузера. На мобильной ширине панель прячется за кнопку
  «☰» в верхней плашке.

### Роли и права
- Администратор может **создавать новые роли** (`/admin` → «Роли и права»
  → «Новая роль») — они появляются в списке ролей при создании
  пользователя.
- Три модульных права — доступ к конструктору журналов, редактирование
  карты критических точек, управление аудитами — теперь хранятся в таблице
  `role_permissions` и включаются/выключаются для любой роли (кроме
  «администратор», у которого доступ всегда есть) прямо в интерфейсе, без
  правки кода.
- **Важная граница возможностей, о которой стоит знать:** право заполнять
  или проверять конкретный журнал по-прежнему определяется текстовыми
  полями «заполняет»/«проверяет» в паспорте журнала (раздел 6 спецификации)
  и явным назначением журнала пользователю, а не новой системой
  `role_permissions`. Другими словами, «Роли и права» управляют доступом к
  трём административным инструментам (конструктор/карта/аудиты), а не
  тем, кто какие журналы может заполнять — это разные механизмы, и я их
  сознательно не объединял, чтобы не переписывать весь модуль записей.

## Что реализовано полноценно
(без изменений из прошлой версии + всё из раздела выше)
- Аутентификация, сессии, блокировка пользователей.
- Универсальный движок журналов с версионированием схемы полей.
- Жизненный цикл записи, отклонения, обязательный комментарий-причина,
  история изменений.
- Модуль несоответствий: 5 статусов, разделение обязанностей, корректирующее
  действие.
- Прослеживаемость партий.
- Карта критических точек как панель контроля.
- Конструктор полей.
- Модуль аудита: план, чек-лист, автосоздание несоответствий, отчёт,
  отправка и ответ ответственного.
- Персональная видимость журналов, фильтры и сортировки, два вида записей.
- Динамические роли и права поверх фиксированной базовой модели.
- Фото/файл-подтверждение к записям и пунктам чек-листа аудита.
- Библиотека шаблонов чек-листов: готовые наборы, донастройка, создание своих,
  применение к конкретному аудиту.

## Что НЕ реализовано
- Экспорт в PDF/Excel — только CSV для «Доказательной базы».
- E-mail-уведомления — просрочки только логируются в консоль раз в час;
  «отправка отчёта ответственному» в аудите — это смена статуса в системе
  и появление задачи на его дашборде, а не письмо на почту.
- Привязка точки карты к отчёту — справочная (список кодов), без
  автоматической фильтрации содержимого отчёта по этой точке.
- Периодичность как структурное поле — по-прежнему разбирается эвристикой
  по тексту.
- Полноценный табличный редактор для индикаторных таблиц (тип Т3).
- Фильтрация записей на уровне SQL (сейчас — в памяти приложения после
  выборки, см. выше).
- Резервное копирование — настройте `pg_dump` по расписанию отдельно.
- Загруженные файлы: нет проверки на вирусы, нет ограничения по типу файла
  (кроме размера — 15 МБ), нет удаления файла при удалении записи (в системе
  вообще нет удаления записей — раздел 10 основного ТЗ). Если при сохранении
  записи с фото форма не прошла валидацию по другому полю, уже загруженный
  файл остаётся на диске «осиротевшим» — небольшая, но известная недоработка
  прототипа. Резервным копированием файлов (`uploads/` / том `mersi-uploads`)
  нужно озаботиться отдельно от `pg_dump`.

## Что стоит проверить в первую очередь после установки

1. `npm run seed` — должен вывести создание 106 журналов, назначение
   журналов демо-пользователям и создание демо-аудита.
2. Вход под `operator` → «Журналы» — должны быть видны только журналы
   группы «Производственные»/операторские (не вся библиотека).
3. Вход под `admin` → «Администрирование» → «Роли и права» — создать
   тестовую роль, выдать ей доступ к конструктору, создать пользователя с
   этой ролью, убедиться что пункт «Конструктор» появился у него в меню.
4. `/audits/new` (под `quality` или `admin`) → создать аудит → «Начать» →
   добавить пункт чек-листа с результатом «Замечание» → должно появиться
   связанное несоответствие → «Завершить» → «Отправить» → войти под
   пользователем-ответственным → должна появиться форма ответа на
   дашборде и на странице аудита.
5. На странице журнала — переключить вид «Таблица» и проверить, что
   столбцы соответствуют полям схемы, а сортировка по клику на заголовок
   работает.
6. Свернуть/развернуть левую панель — состояние должно сохраняться после
   перезагрузки страницы (localStorage).
7. Зайти в «Инструменты» → «Конструктор» — раньше это падало с ошибкой
   (отсутствующая вьюха), теперь должен открыться список журналов с
   кликабельными названиями.
8. Добавить журналу поле типа «Фото/файл-подтверждение» через конструктор →
   создать запись → приложить фото → открыть запись → фото должно
   отображаться превью-картинкой.
9. Открыть аудит в статусе «Идёт» → «Применить готовый чек-лист» → выбрать
   один из 3 засеянных шаблонов → пункты должны появиться в разделе
   «Ожидают ответа» → ответить на пункт с результатом «Замечание» →
   должно создаться несоответствие, пункт — переместиться в «Отвечено».
10. `/checklist-templates` → открыть любой шаблон → добавить/удалить/
    переставить пункт → изменения должны сохраняться.
